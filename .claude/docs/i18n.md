# Localized messages

Every string a user sees is a key in `src/i18n/messages/en.json`; the other `<code>.json` files in
that directory are LibreTranslate's output, hand-corrected where it was wrong, and committed.
`src/i18n/messages/index.ts` is generated too: one `import x from "./x.json" with { type: "json" }`
per file (the only JSON import form NodeNext accepts; tsc then emits the JSON into `dist/`, so the
image needs no copy step) and a `messages` table typed `Record<string, Partial<Messages>>`.

## Runtime

`createI18n(table)` (`src/i18n/index.ts`) → `forLocale(discordLocale)` → `Translator { language,
t(key, params) }`. The table language is picked with `resolveTarget()` against the file set, so
`zh-TW` → `zh-Hant` if that file exists else `zh-Hans`, `no` → `nb`, anything else → `en`. A key a
file lacks falls back to the English value; `{param}` placeholders are interpolated and an unknown
one stays visible. `AppContext.i18n` carries the real table; `makeContext()` builds one from
`src/fixtures/messages.fixture.ts` (partial `fr`, `zh-Hans`, `nb`) so handler tests assert French
output without depending on generated files. `staticI18n` serves module-level command builders.

Handlers: `const tr = ctx.i18n.forLocale(interaction.locale)` (the mention trigger uses
`guild.preferredLocale`; messages carry no user locale), then `tr.t("...")` for notices,
`buildTranslationReply({ ..., tr })`, `userMessageFor(err, tr)`, and `tr.language` wherever a
language name or hint is involved (`labelFor`, `menuLanguages`, `parseLanguageHint`).

Command metadata: `localizationsFor(key, max)` (`src/i18n/discord.ts`) builds the map for
`setDescriptionLocalizations` / `setNameLocalizations`, dropping values that equal English or exceed
the limit (100 for descriptions, 32 for a context-menu name) because the builder validates at
module load. Command *names* stay English; `interaction.commandName` is the default name.

## Writing a message

- Plain sentences. Keep glue in code: `→`, `…`, ` · `, `(NN%)`, bold/backtick line formats. Argos
  eats or rewrites symbols and trailing tokens.
- `{param}` for anything code substitutes; backtick spans for literal syntax in embed text.
  Command descriptions are plain text on Discord's side, so literal syntax there arrives as params
  (`{form}`, `{example}`) and the description holds no backticks.
- Keep the English wording stable: tests assert it, and a changed key is retranslated only with
  `--force` or by deleting it from the other files.

## Generating the other languages

`yarn locales:generate` (`scripts/generate-locales.ts`). LibreTranslate has no host port, so each
request is a small ES-module program piped to `docker compose exec -T bot node --input-type=module -`
with its payload embedded in the source (stdin *is* the program); the stack must be up. Flow per
language reported by `/languages` and reachable from `en`: fill keys missing from `<code>.json`
(all keys with `--force`; `--only fr,de` limits the set), `protect()` placeholders and code spans
as `XZ<n>XZ` tokens (the shape measured to survive every Argos model), batch-translate, `restore()`.
A lost token keeps the English value and is listed as "kept English (fix by hand)". Stale keys are
dropped. `index.ts` is rewritten from the files on disk. `--check` needs no docker and exits 1 when
any file is missing keys.

Locally `LT_LOAD_ONLY` limits which files can be produced; the full set needs every model loaded
(the VPS, or unset it locally). Expect to hand-fix a few strings after a run: Argos leaves
fragments untranslated ("defaults to your Discord language"), drops clauses, or invents words
("Auto-dececto"). Hand edits survive later runs because only missing keys are filled.

Tests: `src/i18n/index.test.ts` checks every file has only known keys, no empty values and the same
placeholder set as `en`; `src/i18n/segments.test.ts` covers protect/restore.

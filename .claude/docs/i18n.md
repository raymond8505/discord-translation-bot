# Localized messages

Every string a user sees is a key in `src/i18n/messages/en.json`; the other `<code>.json` files in
that directory are LibreTranslate's output, hand-corrected where it was wrong, and committed.
`src/i18n/messages/index.ts` is generated too: one `import x from "./x.json" with { type: "json" }`
per file (the only JSON import form NodeNext accepts; tsc then emits the JSON into `dist/`, so the
image needs no copy step) and a `messages` table typed `Record<string, Partial<Messages>>`.

## Runtime

`createI18n(table)` (`src/i18n/index.ts`) hands out a `Translator { language, displayLanguage,
t(key, params) }` through two constructors:

- `forLocale(discordLocale)` — for a reader Discord named, i.e. an interaction.
- `forLanguage(code)` — for a reader named only by a backend code: a flag's language, a target
  someone asked for. Resolved with `resolveLanguageCode()`, so it inherits the menus'
  preferred-first fallback (`zh-Hant` → `zh-Hans` → `zh`).

**`language` and `displayLanguage` are not the same language, and the difference is the point.**
`language` picks the sentences and can only ever be one of the seven files (`resolveTarget()` /
`resolveLanguageCode()` against the file set: `zh-TW` → `zh-Hant` if that file exists else
`zh-Hans`, `no` → `nb`, anything else → `en`). `displayLanguage` names *languages*, and ICU can do
that in any locale Discord sends, so it is the raw locale or an ICU-safe form of the code
(`displayLanguageForLocale()` / `icuLanguageFor()` in `src/locale.ts`) and never goes through the
file set. An Italian reader therefore gets English sentences and Italian language names. Pass it
wherever a name or a hint is involved — `labelFor`, `menuLanguages`, `parseLanguageHint`,
`parseLanguageSpec` — and never `language`.

A key a file lacks falls back to the English value; `{param}` placeholders are interpolated and an
unknown one stays visible. `AppContext.i18n` carries the real table; `makeContext()` builds one from
`src/fixtures/messages.fixture.ts` (partial `fr`, `zh-Hans`, `nb`) so handler tests assert French
output without depending on generated files. `staticI18n` serves module-level command builders.

## Which reader a surface is talking to

Three clauses, and every handler is one of them:

- **A public translation is worded in the language it translates into** —
  `buildTranslationReply({ ..., tr: ctx.i18n.forLanguage(target) })`. The people it is for are the
  ones who read that language.
- **An ephemeral answer is worded in `interaction.locale`** — `reply.posted`, a rate-limit notice,
  `select.expired`, `unknownLanguage`. It is addressed to one person. A `/translate` with no channel
  to post to is that case too: the translation itself goes out worded for its single reader.
- **A DM refusal follows the target when the target is known by then**, and the guild's
  `preferredLocale` otherwise. A flag the bot has no language for names nothing, so
  `buildUnsupportedFlagReply()` is the guild's; the reaction trigger's failure notice reads
  `ctx.languages.peek()` rather than awaiting, because reporting a backend failure must not make a
  backend call.

Discord sends a user locale only on interactions — `User` and `Message` carry none — so the mention
and reaction triggers infer the reader from what they were asked for. A 🇫🇷 reaction is someone asking
for French; `@bot french` is too. A bare `@bot` names nothing and falls back to the guild.

The parse that *produces* the target runs before any of that is known, so `parseLanguageSpec` on the
mention trigger reads the **guild's** `displayLanguage`. English names and every code and locale
always match, so only a language named in a third language is lost: `@bot allemand` in an
English-preferred guild does not resolve, and `@bot german` / `@bot de` always do.

Command metadata: `localizationsFor(key, max)` (`src/i18n/discord.ts`) builds the map for
`setDescriptionLocalizations` / `setNameLocalizations`, dropping values that equal English or exceed
the limit (100 for descriptions, 32 for a context-menu name) because the builder validates at
module load. Command *names* stay English; `interaction.commandName` is the default name.

These reach only as far as the message files do, so an Italian user sees an English command
description and then Italian language names inside the reply. Mildly incoherent and not fixable from
here: Discord renders the description, and there is no Italian wording to give it.

## Writing a message

- Plain sentences. Keep glue in code: `→`, `…`, ` · `, `(NN%)`, bold/backtick line formats. Argos
  eats or rewrites symbols and trailing tokens.
- `{param}` for anything code substitutes; backtick spans for literal syntax in embed text.
  Command descriptions are plain text on Discord's side, so literal syntax there arrives as params
  (`{form}`, `{example}`) and the description holds no backticks.
- Keep the English wording stable: tests assert it, and a changed key is retranslated only with
  `--force` or by deleting it from the other files.
- **Changing what a key *means* is not an edit, it is a replacement.** The six translated files keep
  their old value, which now says something the bot no longer does — worse than English, because it
  is confidently wrong. Retire the key (delete it from **all seven** files, adding new keys to
  `en.json`) rather than rewording it in place. Deleting it from `en.json` alone fails
  `src/i18n/index.test.ts`, which requires every file's keys to be a subset of English's.
- New `en.json` keys read as English everywhere until someone runs `yarn locales:generate` with the
  stack up; that is the intended fallback, not a broken state.

## Generating the other languages

`yarn locales:generate` (`scripts/generate-locales.ts`). LibreTranslate has no host port, so each
request is a small ES-module program piped to `docker compose exec -T bot node --input-type=module -`
with its payload embedded in the source (stdin *is* the program); the stack must be up. Flow per
language reported by `/languages` and reachable from `en`: fill keys missing from `<code>.json`
(all keys with `--force`; `--only fr,de` limits the set), `protect()` placeholders and code spans
as `XZ<n>XZ` tokens (the shape measured to survive every Argos model), batch-translate, `restore()`.
A lost token keeps the English value and is listed as "kept English (fix by hand)". Stale keys are
dropped. `index.ts` is rewritten from the files on disk. `--check` needs no docker and exits 1 when
any file is missing keys.

Locally `LT_LOAD_ONLY` limits which files can be produced; the full set needs every model loaded
(the VPS, or unset it locally). Expect to hand-fix a few strings after a run: Argos leaves
fragments untranslated ("defaults to your Discord language"), drops clauses, or invents words
("Auto-dececto"). Hand edits survive later runs because only missing keys are filled.

Tests: `src/i18n/index.test.ts` checks every file has only known keys, no empty values and the same
placeholder set as `en`; `src/i18n/segments.test.ts` covers protect/restore.
